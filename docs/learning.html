1. What are we deciding?

Must every source update continuously, or can some arrive in batches? The assessment names orders, clicks, and CRM data. It asks for real-time analytics and consideration of batch processing, but gives no numerical freshness target.

We need to decide how data should arrive before choosing the services that move it. Otherwise we cannot explain why those services are necessary.

What “fresh” actually means

Freshness is how long a change takes to become available to the person or system using it. Waiting for an export, processing it, loading it, and refreshing a dashboard can all add delay.

Hypothetical example: an order is placed at 10:02. An hourly batch next starts at 11:00. The order waits 58 minutes before processing even starts.

A streaming route can remove that scheduled wait. It still has source, processing, and delivery delays.

Why not choose a one-minute target immediately?

It would be an assumption. First ask what decision needs that freshness, where we measure it, and whether the source can supply it. A target for warehouse availability is different from a target for a refreshed dashboard.

2. Explore the alternatives

Why is the mixed approach our recommendation?

It accommodates both modes named in the brief. It lets the freshness requirement differ by source. But it is defensible only if using an older CRM snapshot is acceptable to the consumer. We must state that limitation rather than calling the entire result “real time”.

Does streaming mean Dataflow is already chosen?

No. Streaming is a processing approach. Dataflow is one service that supports it. We will separately ask whether we need custom transformations, buffering, and orchestration before assigning those responsibilities to services.

Google’s Dataflow overview confirms support for batch and streaming. It does not establish which option fits our business requirements.

When would we change the recommendation?

If CRM changes must affect immediate decisions, we would investigate incremental or streaming CRM ingestion. If all consumers tolerate longer delays, we would examine whether scheduled batches meet the assessment’s real-time expectation. If a source cannot expose changes reliably, we must resolve extraction first.

3. Can you spot the consequence?

A customer's CRM region changes at 09:30. Our latest CRM snapshot is from 09:00. Their new order arrives at 10:02 and is processed immediately.

If we join that order to the CRM snapshot, is its region current?

Reveal the reasoning after you have tried

No. Fast order processing does not make the CRM snapshot current. We have combined a fresh event with an older attribute.

We could refresh CRM more often, capture changes, or use the region recorded on the order if the metric is about where the order occurred. The last option changes the meaning of the analysis, not just the technology.

The sample calls the field OrderRegion. We should not silently substitute a customer's current region. This is a concrete example of a decision we must justify before writing a transformation.
