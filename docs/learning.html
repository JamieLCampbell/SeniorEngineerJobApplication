Why replace the table instead of append?

This file is our complete assessment snapshot. Appending it again would double the number of orders. Replacement gives the same result on a rerun. An incremental source needs a different design: stage new records and merge by an agreed business key.

Why use a loader service account?

Terraform needs infrastructure permissions; loading data does not. The batch uses a short-lived token for an identity limited to its bucket, dataset and query jobs. No private service-account key is stored. The developer login still has broader deployment access.

Every query is dry-run first and has a server-side 10 MiB scan limit. This protects these jobs from unexpectedly scanning a large table. It is not a spending cap for the account and does not cover storage or queries launched elsewhere.

What does a 30-day average actually mean?

First calculate each accepted order's total: unit price multiplied by quantity. Order 104 is 350 × 4 = 1400. Missing quantity cannot become one without inventing a fact.

Why use a calendar range?

On 30 January, include 1–30 January. On 31 January, include 2–31 January. A window of 30 rows would count orders instead of days: a busy customer could have 30 orders in one afternoon.

What is the denominator?

We chose the number of accepted orders in that period. Two orders worth 100 and 200 give an average order value of 150. Average daily spending is a different question: it would require a calendar and a decision about days without purchases.

Why include all orders on the same date?

The source has no time of day. We cannot say which purchase happened first, so every order on that date sees the same window and average.

Python cleaning: convert evidence, preserve uncertainty

The functions now parse fields, validate rows, and handle repeated IDs separately from reading and writing files. The same cleaner can later feed a cloud upload without duplicating the rules.

Why reject unknown dates and amounts?

We cannot recover them from the sample. Setting an amount to zero invents a free order; choosing a date invents when it happened. We preserve the original record and reasons outside the accepted dataset. The resulting analysis covers accepted records, not all sales.

Why are missing product IDs allowed?

The supplied order amount and region can still be preserved without knowing the product. We keep a null and a warning. Quantity is required because total value is calculated as unit price times quantity.

Why separate parsing from cleaning?

A parser answers “can this value become a valid number or date?” The cleaner answers “does this order meet our acceptance rules?” File handling answers “how do we read and save it?” Those are reusable responsibilities without a large framework.

Why not keep the last version of an order?

The source has no update timestamp. File order is not reliable evidence of which conflicting version is correct. We reject every version of a conflicting ID, but remove valid equivalent repeats with a record of what was retained.

Terraform: repeat the design safely

Terraform describes the resources we want. A plan shows proposed changes; apply carries them out. We have applied dev and verified it in GCP. Pre/prod remain locally validated configurations.

Dev is for experiments. Pre is a rehearsal using the same code and production-style guards. Prod receives the reviewed revision. Each uses its own project, state, data, and identity.

Why one module and three small entry points?

The module defines the bucket, dataset, table and loader once. Each environment supplies its project and policy values. That reduces drift while making the target visible in commands. We accept a little repeated root configuration rather than hiding the environment in a selected workspace.

What is Terraform state?

State maps the code to real cloud resources. Each environment needs its own private state. We use a separate pre-existing GCS state bucket per environment with locking and versioning, and keep state out of Git. Resource names alone do not prevent one environment's identity from accessing another: project IAM must provide that boundary.

Why does pre have production-style protections?

We want to discover replacement and deployment problems before prod. Dev permits deliberate table replacement; pre and prod guard table and bucket deletion through Terraform. Those guards do not stop all API deletes or scheduled object expiry. Their scope matters.

Why are retention values different?

The dev and pre examples use short-lived synthetic data: seven and fourteen days. Production requires an explicit policy; the example of ninety days is only illustrative. Soft delete retains deleted objects for another period, so lifecycle expiry is not a promise of immediate erasure.

Check your understanding: if the same code works in dev, can we apply its saved plan directly to prod?

Reveal the answer

No. Promote the same Git revision, then create and review a new plan against prod's project, inputs, and state. The dev plan targets dev resources.

Read the setup, scope, and promotion instructions. Only the batch foundation is included; the full streaming architecture is not being provisioned.

Can we trust it when something fails?

Our operating choices are deliberately small: separate service identities, restricted source data, useful alerts, retained inputs for recovery, and limits on unnecessary spending.

Why separate identities?

A website collector needs to publish events. It does not need to delete customer exports or change analytical tables. Separate identities let us grant each component only the access needed for its job. Analysts read curated data rather than receiving broad access to raw customer records.

What should trigger investigation?

A growing event backlog, stalled order replication, missing CRM export, or sudden increase in rejected records. A green job status is not sufficient: compare input, accepted, and rejected counts, and investigate failed writes. Exact alert thresholds need actual freshness requirements and normal traffic.

How do we recover clickstream events?

A separate Pub/Sub Cloud Storage subscription archives payloads and metadata independently of the processing job. We must monitor the archive too: successful processing does not prove that archiving succeeded. Replays require stable event IDs and duplicate-safe writes. A retained file is useful input, not a complete recovery procedure by itself.

Where do costs grow?

Continuously running services, retained data, and large queries. Keep Composer and streaming Dataflow in the proposed architecture, but do not deploy them for ten CSV rows. For larger analytical tables, use suitable date filters and partitioning; check query estimates and limit bytes billed.

Check your understanding: Dataflow is running, but every event is being rejected. Is the pipeline healthy?

Reveal the answer

No. Infrastructure uptime and useful data delivery are different things. The rejected-event rate and accepted count reveal the problem. Investigate the rule or source schema before assuming more computing capacity will help.

Composer: coordinate the batch steps

We chose Composer for the proposed platform's batch jobs: confirm export ready → load staging → validate → publish if checks pass.

Composer uses Airflow to describe task dependencies. BigQuery loads and transforms the records; Composer starts that work and checks whether it finished. It does not need to handle each click or database change.

What is a DAG?

A directed acyclic graph is a set of tasks with dependencies that do not loop back on themselves. In our example, publication depends on successful validation, which depends on a successful load. The graph expresses the order in which work may happen.

Why Composer rather than a simpler schedule?

It gives the platform a place to manage dependent jobs, inspect failures, and rerun selected work. The trade-off is environment cost and maintenance. Workflows with Cloud Scheduler can also coordinate and retry this short sequence, and may be the better choice if that is all the platform needs. We are including Composer with a defined responsibility, not assuming the brief's service list proves it is necessary.

Will we deploy Composer for the assessment?

No. We will run the Part 2 Python pipeline manually. The architecture describes how a wider platform would operate; the small coding task does not need a managed Airflow environment.

Does retrying a task make it safe?

No. If a load appends the same export twice, an automatic retry can duplicate customer records. The load must identify its input and safely replace or reuse its staged result. Likewise, an older rerun must not overwrite a newer report.

Check your understanding: the staging load succeeds, but the export fails the completeness check. Should the reporting table be refreshed?

Reveal the answer

No. Stop publication, show the failure, and keep the last good report with its original source timestamp. Retrying the same incomplete export will not repair it. A temporary service failure is different and can justify a bounded retry.

CRM batches: keep the file, check the load

We chose CRM export → Cloud Storage → BigQuery staging → SQL validation → reporting tables.

Cloud Storage holds the original file. Staging is a separate table where an import can be checked before reports use it. SQL handles the tabular rules without another processing service.

Why keep the original export?

If we discover an incorrect cleaning rule, we can reload the file and try again. A direct load could be simpler, but we would depend on the CRM or connector to reproduce that earlier input. Keeping files also adds storage and privacy responsibilities, so retention must be finite and access restricted.

Why not load straight into the report?

A partial or invalid import could replace good data. Instead, validate the staged snapshot first, then publish it. If validation fails, keep the previous report and its original freshness timestamp so users can see that it has not advanced.

What does a snapshot mean?

A complete export describes the customer dataset at a point in time. That is our working assumption. An incremental file contains only changes, so replacing the whole report with it would lose unchanged customers. We must confirm the CRM export behaviour before implementing the load.

How do reruns stay safe?

Identify the export and rebuild its staged result instead of appending the same rows twice. Only a newer validated snapshot should advance the current report. Replaying an older file can help investigation, but must not silently roll the current report backwards.

Check your understanding: yesterday's customer export is loaded successfully at noon today. Is the customer data fresh as of noon?

Reveal the answer

No. Load time describes our processing. The source snapshot time describes the age of the customer data. Keep both, and show consumers the source time. We have not yet chosen the export frequency or retention period.

Clickstream: collect, buffer, process

We chose website → collection endpoint → Pub/Sub → Dataflow → BigQuery.

A product-view event first reaches our server endpoint. The endpoint checks the request and publishes it. Pub/Sub holds the published message for the processing subscription. Dataflow applies the event rules and writes the accepted record to BigQuery.

Why have an endpoint as well as Pub/Sub?

The browser sends an HTTP request to our collection endpoint. The server holds permission to publish to the cloud; we do not put cloud credentials in the browser. This endpoint might live in the existing website backend. We have not chosen another hosting service just for the diagram.

What does the buffer buy us?

If processing slows down, already published events can wait in Pub/Sub within its configured retention limits. Collection and processing do not have to run at exactly the same speed. We must still monitor backlog age: a growing queue means users are seeing older data.

Why Dataflow, and when would we remove it?

It gives us a place for event-specific validation, supported field conversion, and rejected-record handling. We accept another running job and its cost. If the actual event schema needs only simple conversion, a direct BigQuery subscription may be enough. Basic cleaning does not automatically justify Dataflow; our custom processing requirement must survive review.

What happens to a bad timestamp?

A recognised format can be converted. A value we cannot interpret goes to a separate restricted output with a reason. We do not invent the time, silently drop the event, or retry a permanently invalid value forever. A temporary storage failure is a different problem and must be surfaced and retried appropriately.

Check your understanding: the endpoint publishes successfully, but the browser never receives its response and retries. Can two messages describe the same click?

Reveal the answer

Yes. Preserve the same event ID across retries so duplicate business events can be recognised. Pub/Sub buffering alone does not solve that problem. We still need to define duplicate handling and how long identifiers must be remembered before deployment.

Our next decision: CDC for orders

CDC means Change Data Capture. After copying the existing data, we capture ongoing database changes so the analytical copy can follow the source.

Our working route is database → Datastream → BigQuery replica → analytical SQL. Datastream supports a direct BigQuery destination; this route does not need Pub/Sub and Dataflow in the middle.

Why choose this over application events?

The brief gives us transactional databases, but does not say we can modify the shop application. CDC captures changes at the database level. Application events would give clearer business meanings, such as “payment accepted”, but require application integration and reliable publishing. A changed row does not always explain the business action behind it.

What does the initial copy do?

It brings in existing orders. Without that backfill or another initial load, capturing only future changes would not provide the complete starting dataset. Datastream supports backfill alongside ongoing replication.

What happens when an order changes or is deleted?

Our working choice is merge mode with a supported primary key: an update changes the replicated row, and a delete removes it from current state. We therefore cannot call this replica a permanent audit history. If we need every earlier version, we must design history retention separately.

What could stop this design working?

We still need the actual database engine and version, a suitable primary key, replication permissions/settings, and network access. CDC is the selected approach; Datastream compatibility is an assumption to verify. Replication also does not fix missing values or decide what a metric means.

Check your understanding: if a source order is deleted, should we expect to find its original version in a current-state replica?

Reveal the answer

No. The replica follows source state. A permanent historical record needs an explicit history or archival design. Keeping the original order region protects against customer-profile changes, but does not itself preserve a deleted order.

1. What are we deciding?

Must every source update continuously, or can some arrive in batches? The assessment names orders, clicks, and CRM data. It asks for real-time analytics and consideration of batch processing, but gives no numerical freshness target.

We need to decide how data should arrive before choosing the services that move it. Otherwise we cannot explain why those services are necessary.

What “fresh” actually means

Freshness is how long a change takes to become available to the person or system using it. Waiting for an export, processing it, loading it, and refreshing a dashboard can all add delay.

Hypothetical example: an order is placed at 10:02. An hourly batch next starts at 11:00. The order waits 58 minutes before processing even starts.

A streaming route can remove that scheduled wait. It still has source, processing, and delivery delays.

Why not choose a one-minute target immediately?

It would be an assumption. First ask what decision needs that freshness, where we measure it, and whether the source can supply it. A target for warehouse availability is different from a target for a refreshed dashboard.

2. Explore the alternatives

Why is the mixed approach our recommendation?

It accommodates both modes named in the brief. It lets the freshness requirement differ by source. But it is defensible only if using an older CRM snapshot is acceptable to the consumer. We must state that limitation rather than calling the entire result “real time”.

Does streaming mean Dataflow is already chosen?

No. Streaming is a processing approach. Dataflow is one service that supports it. We will separately ask whether we need custom transformations, buffering, and orchestration before assigning those responsibilities to services.

Google’s Dataflow overview confirms support for batch and streaming. It does not establish which option fits our business requirements.

When would we change the recommendation?

If CRM changes must affect immediate decisions, we would investigate incremental or streaming CRM ingestion. If all consumers tolerate longer delays, we would examine whether scheduled batches meet the assessment’s real-time expectation. If a source cannot expose changes reliably, we must resolve extraction first.

3. Our decision: use the order's region

Historical regional spending uses OrderRegion directly. We will not replace it with current CRM region, so a customer moving later does not reassign an earlier sale.

Weigh the alternatives

Order region: directly available and stable when customers move, but inherits errors in the order source. This is our choice for historical sales.

Current CRM region: useful for today's customer segmentation, but moves past spending between regions and depends on snapshot freshness.

CRM region at order time: useful when historical customer attributes are required, but needs dated history, valid timestamps, and checks that each order matches no more than one history row.

We will leave a missing order region unresolved for the quality policy rather than fill it from current CRM. A deliberate correction to the source order is different from a customer moving.
