Our next decision: CDC for orders

CDC means Change Data Capture. After copying the existing data, we capture ongoing database changes so the analytical copy can follow the source.

Our working route is database → Datastream → BigQuery replica → analytical SQL. Datastream supports a direct BigQuery destination; this route does not need Pub/Sub and Dataflow in the middle.

Why choose this over application events?

The brief gives us transactional databases, but does not say we can modify the shop application. CDC captures changes at the database level. Application events would give clearer business meanings, such as “payment accepted”, but require application integration and reliable publishing. A changed row does not always explain the business action behind it.

What does the initial copy do?

It brings in existing orders. Without that backfill or another initial load, capturing only future changes would not provide the complete starting dataset. Datastream supports backfill alongside ongoing replication.

What happens when an order changes or is deleted?

Our working choice is merge mode with a supported primary key: an update changes the replicated row, and a delete removes it from current state. We therefore cannot call this replica a permanent audit history. If we need every earlier version, we must design history retention separately.

What could stop this design working?

We still need the actual database engine and version, a suitable primary key, replication permissions/settings, and network access. CDC is the selected approach; Datastream compatibility is an assumption to verify. Replication also does not fix missing values or decide what a metric means.

Check your understanding: if a source order is deleted, should we expect to find its original version in a current-state replica?

Reveal the answer

No. The replica follows source state. A permanent historical record needs an explicit history or archival design. Keeping the original order region protects against customer-profile changes, but does not itself preserve a deleted order.

1. What are we deciding?

Must every source update continuously, or can some arrive in batches? The assessment names orders, clicks, and CRM data. It asks for real-time analytics and consideration of batch processing, but gives no numerical freshness target.

We need to decide how data should arrive before choosing the services that move it. Otherwise we cannot explain why those services are necessary.

What “fresh” actually means

Freshness is how long a change takes to become available to the person or system using it. Waiting for an export, processing it, loading it, and refreshing a dashboard can all add delay.

Hypothetical example: an order is placed at 10:02. An hourly batch next starts at 11:00. The order waits 58 minutes before processing even starts.

A streaming route can remove that scheduled wait. It still has source, processing, and delivery delays.

Why not choose a one-minute target immediately?

It would be an assumption. First ask what decision needs that freshness, where we measure it, and whether the source can supply it. A target for warehouse availability is different from a target for a refreshed dashboard.

2. Explore the alternatives

Why is the mixed approach our recommendation?

It accommodates both modes named in the brief. It lets the freshness requirement differ by source. But it is defensible only if using an older CRM snapshot is acceptable to the consumer. We must state that limitation rather than calling the entire result “real time”.

Does streaming mean Dataflow is already chosen?

No. Streaming is a processing approach. Dataflow is one service that supports it. We will separately ask whether we need custom transformations, buffering, and orchestration before assigning those responsibilities to services.

Google’s Dataflow overview confirms support for batch and streaming. It does not establish which option fits our business requirements.

When would we change the recommendation?

If CRM changes must affect immediate decisions, we would investigate incremental or streaming CRM ingestion. If all consumers tolerate longer delays, we would examine whether scheduled batches meet the assessment’s real-time expectation. If a source cannot expose changes reliably, we must resolve extraction first.

3. Our decision: use the order's region

Historical regional spending uses OrderRegion directly. We will not replace it with current CRM region, so a customer moving later does not reassign an earlier sale.

Weigh the alternatives

Order region: directly available and stable when customers move, but inherits errors in the order source. This is our choice for historical sales.

Current CRM region: useful for today's customer segmentation, but moves past spending between regions and depends on snapshot freshness.

CRM region at order time: useful when historical customer attributes are required, but needs dated history, valid timestamps, and checks that each order matches no more than one history row.

We will leave a missing order region unresolved for the quality policy rather than fill it from current CRM. A deliberate correction to the source order is different from a customer moving.

No. Fast order processing does not make the CRM snapshot current. We have combined a fresh event with an older attribute.

We could refresh CRM more often, capture changes, or use the region recorded on the order if the metric is about where the order occurred. The last option changes the meaning of the analysis, not just the technology.
