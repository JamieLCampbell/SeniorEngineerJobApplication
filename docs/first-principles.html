01 · THE PURPOSE

Operational data and analytical data

Running the shop

The checkout records an order and its payment status. It needs reliable, fast updates for one transaction.

Understanding the shop

An analyst compares spending across thousands of orders, regions, and dates.

A data platform prepares trustworthy records for those broader questions.

Discuss: what business decision would benefit from seeing an order within a minute?

Speaking notes

Copying data for analytics gives us a place to standardise definitions and manage reporting workloads. The business outcome determines how fresh the data needs to be. A monthly regional report and an operational dashboard may have very different needs.

03 · DATA MOVEMENT

Batch and streaming

Batch: process a bounded collection

Read yesterday’s CRM export, transform its rows, and finish.

Benefit: straightforward reruns and scheduling.

Cost: data waits for the next run.

Streaming: process arriving events

Keep processing as clicks and orders arrive throughout the day.

Benefit: fresher analytical data.

Cost: ongoing operation, retries, and late events.

Discuss: does every source need the same freshness?

Speaking notes

Batch and streaming describe how work arrives; neither automatically makes data correct. A small scheduled batch can be sufficient when a few minutes of delay are acceptable. Dataflow supports both approaches. Dataflow overview.

04 · INGESTION

Pub/Sub: a buffer between systems

Checkout publisher → Pub/Sub topic → subscription → consumer

A producer publishes an event. A consumer receives it and acknowledges successful handling.

Why it helps: the checkout and the analytical processor can run at different speeds.

Trade-off: backlog, retries, and duplicate handling become part of the design.

Speaking notes

A topic is a named destination for messages. A subscription tracks delivery to a consumer group; separate subscriptions allow independent consumers. We would use one processing subscription and a separate archive path. Application event IDs are still needed to identify repeated business events. A subscription’s delivery behaviour alone does not prove end-to-end uniqueness. Pub/Sub overview.

Transactional database changes also require a source mechanism: application events, an outbox publisher, or database change capture. Connecting a box labelled database to Pub/Sub does not implement that mechanism.

05 · PROCESSING

Dataflow: apply rules as data moves

Incoming event → validate → standardise → route to an output

Our proposed pipeline checks required fields, converts supported values, and separates accepted records from records needing investigation.

Why Dataflow: managed execution for batch and streaming pipelines at scale.

Trade-off: additional pipeline code and operating cost. A small CSV task can use a local Python script.

Speaking notes

Apache Beam is a programming model for pipelines; Dataflow is a managed service that can run them. We choose Dataflow for the proposed continuous processing workload, not because ten CSV rows require distributed computing. If no custom processing were needed, we would evaluate a more direct ingestion route. Dataflow overview.

07 · ORCHESTRATION

Composer: coordinate the work

Wait for export → start batch job → check results → refresh reporting tables

Orchestration decides when tasks run and what they depend on. The processing jobs perform the transformations.

Composer: a candidate for complex data workflows using Airflow.

Alternative: Workflows for simpler service sequences; a manual run is enough for the initial assessment demo.

Speaking notes

A DAG is a graph of tasks with dependencies and no circular path. Composer can start a Dataflow job or a BigQuery query. It does not need to sit in the path of every streaming event. Include it in the proposed design for scheduled CRM loads and backfills, then explain why we are not provisioning it for the small demonstration. Google’s orchestration comparison.

08 · PROPOSED ARCHITECTURE

How the services fit together

Orders / clicks → publisher → Pub/Sub → Dataflow → BigQuery

Pub/Sub → independent archive consumer → Cloud Storage

CRM export → Cloud Storage → batch processing → BigQuery

Composer coordinates scheduled batches and replay jobs. Analysts and offline model training read curated BigQuery data.

Conceptual routes. Source connectors, archive implementation, and recovery behaviour remain design decisions.

Speaking notes

Use separate subscriptions for processing and archiving so they can progress independently. Archive success and warehouse success are separate outcomes: monitor both and reconcile counts or event IDs. Replays read archived inputs and apply idempotent writes, meaning that repeating the same operation has the same final effect. The batch processor can be Dataflow at scale; our small implementation uses Python. This is a teaching overview, not the final detailed architecture diagram.

09 · CORRECTNESS

Delivery time and event time

An order happens at 10:00, but arrives at 10:07 after a network interruption.

Event time

When the business event occurred. Usually the useful date for spending analysis.

Processing time

When our pipeline handled it. Useful for monitoring freshness and delays.

Discuss: when late orders arrive, should yesterday’s reported total change?

Speaking notes

We must define correction rules and an acceptable lateness policy. A duplicate delivery is also different from two legitimate orders with equal amounts. Store source IDs and timestamps so we can investigate both. Do not claim that a single exactly-once setting makes the entire business process duplicate-free.

11 · SECURITY AND OPERATIONS

Trust includes access and recovery

  • Access: separate pipeline identities from analyst access; grant only the permissions each needs.
  • Privacy: keep raw customer data restricted and publish only necessary analytical fields.
  • Monitoring: track freshness, backlog, rejected records, and failed writes.
  • Recovery: preserve replayable inputs and reconcile results after reruns.
Speaking notes

These are proposed design controls. We still need to specify roles, retention periods, and recovery targets. For each metric, ask who acts on it and what they do. Monitoring a running job is insufficient if it is silently rejecting every order. Local authentication should use Application Default Credentials rather than committed keys. Local authentication guidance.
